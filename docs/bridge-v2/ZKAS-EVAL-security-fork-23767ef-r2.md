## 1. Verdict

This is a **mandatory consensus hard fork with a date**, not a maintenance release, and it lands on both of Kron's zKAS-side artifacts:

1. **Node + walletd must be on this release before mainnet DAA 8,614,100** (≈ 2026-11-03 10:00 UTC at 1 BPS — the coinbase-tag ban start, `2 × finality_depth` before the fork). The fork itself activates at **8,700,500** (≈ 2026-11-04 10:00 UTC). A v1.0.8 node that keeps running past the fork follows the old rules there and the new build then **refuses to start on that datadir** ("Delete the data directory and resync, or restore a snapshot taken before the fork") — `consensus/src/consensus/mod.rs:492–506`. So the upgrade window is *before* the fork, and a pre-fork datadir snapshot is the rollback.
2. **The bridge must change how it builds the aux witness, gated per template on DAA ≥ 8,700,500.** From the fork the legacy `ZKMM || hex(H_fc)` form is **rejected** (`consensus/pow/src/auxpow.rs:83–96`: `AuxRule::Bound` requires `committed_hash().is_none()`, i.e. *no* `ZKMM` in the parent coinbase at all). Every merged zKAS submission from an unported bridge fails proof-of-work from block 8,700,500 on; KAS-side mining is unaffected. Upstream's own `bridge/` directory is **unchanged since 2026-07-22** (`a0908f5`), so there is no upstream bridge patch to port — the port is ours to write (§3).
3. **The reward model changes at the fork**: blue rewards pass through a per-script *accrual slot* and are paid as one note per streak or every 100 DAA (§4). The per-block `is_accepted = payment copy` rule in `zkas_blocks` and the reporter's "latest walletd coinbase" amount source stop mapping one note to one block.

Dates are from the DAA pin in the commit (`params.rs:925`: set at mainnet DAA 6,313,429 on 2026-10-07) extrapolated at exactly 1 BPS; the real block rate drifts, so treat them as ±1 day and read the live DAA before scheduling anything (est. DAA at write time ≈ 6.57M). Upstream's constraint: "moving it later is a full release; it can never move earlier."

There is no release to deploy yet. The action now is preparation (§6), not a cutover.

## 3. Bridge port required (our fork, `IndyDaredevil/zkas-rusty-kd`)

Current form (BRIDGE-SPEC-v2.0.1.4 §3.3, NODE-CONTRACT §4.4): compute `H_fc` over the zKAS template header, embed `ZKMM || hex(H_fc)` once in the **KAS** coinbase `extra_data`, mine the KAS header against zKAS bits, submit the solved parent to KAS as a normal block and to zKAS as an aux block over the RpcRawHeader/wRPC path.

Post-fork form, read from `miner/src/merged.rs:68–91` (`build_aux_pow_bound`, upstream's reference implementation for its own miner) and the verifier:

1. At zKAS template build, if `template.header.daa_score ≥ 8,700,500`: `nonce_free = hash_override_nonce_time(&header, 0, header.timestamp)`; `commitment = AuxPow::bound_commitment(genesis_hash, nonce_free)`; embed `ZKM1 || hex(commitment)` in the KAS coinbase `extra_data` — **and no `ZKMM`**. Below that score: unchanged legacy path.
2. After the KAS solve: `header.nonce = AuxPow::nonce_binding(&parent_header)` (first 8 LE bytes of the parent header hash, recomputed from fields), then `header.finalize()` — **the zKAS block hash changes at this step**, so anything the bridge logs or submits as `H_fc` must be the post-nonce hash (the `DOUBLE! … H_fc:` line the reporter parses, the share/block log, the `/metrics` block counters).
3. Submit as before. The verifier checks: nonce == binding · no `ZKMM` in parent coinbase · `ZKM1` commitment == `bound_commitment` · Merkle inclusion · parent PoW ≤ target.
4. Straddle: a template built pre-fork and solved post-fork is judged by *its own* `daa_score` (the rule is per header), so no wall-clock race — but the bridge must not cache a pre-fork template across the boundary and rebuild its coinbase (the template cache rebuild rules in `a2b2bee`/`b4f8886` are the node's; the bridge's own cache is ours to check).
5. Sanitizer: `coinbase_tag_suffix` rejects `ZKM1` as well as `ZKMM` (BL-009 class). The zKAS template request's `extra_data` carries neither (ban from 8,614,100; the node refuses the template with a clear message, which the bridge should surface, not retry silently).
6. Where the helpers live: `kaspa_consensus_core::auxpow::{AuxPow, MERGE_MINE_MAGIC_V1}`, `kaspa_consensus_core::hashing::header::hash_override_nonce_time` — in-workspace crates. The fork's lockfile discipline (BRIDGE-SPEC §3.6: kaspa-* crates resolve in-tree) means the port needs **a rebase onto `23767ef` or later** first; merge-base with upstream is `3049252` (2026-08-04, ZKAS-EVAL-v1.0.9-r1 §7), and none of v1.0.8/9/10 is an ancestor of the fork. That rebase was queued "when firecash carries v2.1.0" — this fork moves it ahead of that trigger.
7. Genesis hash: read from the node's params at runtime or pin from `MAINNET_PARAMS.genesis` — never typed.

Test plan the port owes (not written here): the invariant-7 magic-byte test gains a `ZKM1` twin; a unit test that a header built pre-fork decodes byte-identically (`b4f8886` claims this for bundles; the bridge's own serialization is separate); a devnet/simnet run across an activation score (devnet fork at 1,500 — `params.rs:1281`; simnet `always`), which is the only end-to-end check available before the mainnet date.

Upstream watch: `firecash/zkas-pool` and `solo-dual-mode` (ledger: pool/bridge upstream) have not been read for this eval; if upstream ships a bound-form bridge there, re-diff before porting (BL-005 class — their vendored tree, not their README path).

## 4. walletd / reporter / dashboard effects

- **Send hold**: walletd holds sends for the 600 DAA before the fork (`FORK_BOUNDARY_HOLD`, `zkas-walletd/src/lib.rs:538`) and until a post-fork anchor matures (600-deep, `DEFAULT_ANCHOR_DEPTH`) after it — roughly 10 min each side at 1 BPS, longer if templates are slow. Treasury sends and auto-consolidate (BL-115) sit in that window. `shielded-pay` refuses after the fork outright.
- **Accrual changes note shape** (`processes/coinbase.rs:334–356`): post-fork, Kron's consecutive blues pay **one** output when another script interrupts the streak or at the next multiple of 100 DAA. On a ~19-node network Kron's streaks are short, so most notes will still be one or a few blocks — but the identity "one coinbase note = one block = one `zkas_blocks` row" no longer holds. Affected: `is_accepted` (payment copy per row), the reporter's `provisional amount source: … (latest walletd coinbase)`, the dashboard's per-block amount, and any "red block = absence of payment" inference. The node's rewards RPC "reports the pending slot" (`a2b2bee`), which is the new instrument for what is owed but unpaid.
- **Halving first**: 7,889,400 (≈ Oct 26) is independent of this fork and arrives ~9 days earlier. Expect 35.90774992 → half; the reporter reads the amount from walletd so it follows, but any fixed-subsidy logic (chain-block rule for zKAS, drought thresholds in zKAS terms) needs the new value.
- **Red-reward coinbases**: the template cache "rebuilds post-fork red-reward coinbases" — node-side; no bridge action, but a reason the coinbase must still be used verbatim (NODE-CONTRACT §4.2).
